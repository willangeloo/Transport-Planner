# Working on Transport Planner

## Branches

`main` always holds the version you would show the department. Never commit to it directly: every change goes on its own branch and comes in through a Pull Request.

### Branch names

```
<type>/<short-description>
```

- Use lowercase words separated by hyphens, at most about 40 characters.
- Describe **what** the branch changes. Leave the version number out, because the version is decided when you merge (see Versions below).
- Each branch holds one feature or one fix.

| Type | Use it for | Example |
|---|---|---|
| `feature/` | Something new in the app | `feature/products-manifest` |
| `fix/` | A bug | `fix/save-as-dialog` |
| `improve/` | A change to something that already works (UI, wording, speed) | `improve/report-filters` |
| `refactor/` | Reorganising code with no visible change | `refactor/split-app-script` |
| `data/` | How Excel files are read (new columns, new reports) | `data/uplifts-report` |
| `docs/` | README, guides, this file | `docs/user-guide` |
| `test/` | Tests only | `test/fixed-routes` |
| `chore/` | Repo housekeeping (.gitignore, settings) | `chore/gitignore-pod` |
| `claude/` | Created automatically by Claude sessions | `claude/nifty-galileo-x14whb` |

**Claude sessions:** a session works on the branch it was given, which is usually `claude/<random-name>`. The PR title then says what the change is. If you want a proper name, include it in the request (for example, "work on `feature/products-manifest`").

### Lifecycle

1. Create the branch from the latest `main`.
2. Commit and push. Small commits with clear messages are best.
3. Open a Pull Request into `main`. Title it like `v0.9.2 – Products / manifest` or `Fix: Save as dialog`.
4. Test the HTML from the branch (download it from the PR) and run `tests/` if the change is large.
5. Merge, then delete the branch.
6. If it is a release, tag it (see below).

Don't reuse a branch after its PR is merged. Start a new one from `main`.

## Versions

- There is one file, `Route Planner.html`; old file names like `v0.9.0.html` are no longer used.
- `APP_VERSION` in the file and the header tag must match the release.
- After merging a release, tag `main` as `vX.Y.Z` (for example `v0.9.2`). Older versions can then be downloaded from the tags page.
- Version numbers: **Z** for small fixes, **Y** for new features. **X** moves to `1` when the app leaves BETA.

## Data never goes in the repo

This repository is public. Real customer, order, driver or plan files must never be committed. The `.gitignore` blocks spreadsheets and the data folders, but check the file list in every PR anyway. Tests use only the fake data generated by `tests/fixtures.js`.
